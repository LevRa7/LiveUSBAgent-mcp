# Как защитить пользователей от администратора шлюза

**Дата:** 2026-11-19
**Вопрос:** как сделать так, чтобы админ/оператор шлюза не мог получить доступ к аккаунтам и
устройствам авторизованных пользователей?
**Связанные документы:** [SECURITY_FORK_ASSESSMENT.md](SECURITY_FORK_ASSESSMENT.md),
[remote_harness_mcp_v2_plan.md](remote_harness_mcp_v2_plan.md) (§5 «Криптографическая модель»),
[GOOGLE_OAUTH.md](GOOGLE_OAUTH.md)

---

## 1. Сначала — честная граница возможного

Если шлюз **терминирует MCP** (принимает `tools/call`, видит аргументы и результаты, хранит
link-key, может выдать новый), то оператор этого шлюза **всегда** может действовать от имени
пользователя. Это не баг конкретной реализации, а следствие модели:

> Кто выполняет код на сервере и держит ключи — тот и есть пользователь с точки зрения сервера.

Поэтому «запретить админу» правами доступа, ролями и аудитом **нельзя** — можно только:

1. **убрать у сервера возможность читать/подделывать содержимое** (криптография: E2E);
2. **убрать у сервера возможность выпускать пользовательские ключи** (ключи только у клиента);
3. **сделать сервер доверенным для пользователя** (свой шлюз, аттестация, TEE);
4. **сделать злоупотребление обнаружимым** (аудит с проверкой на стороне клиента).

Всё остальное — снижение вероятности и ущерба, а не устранение.

---

## 2. Модель угроз

| Актор | Что имеет | Чего мы хотим не допустить |
| :--- | :--- | :--- |
| Оператор шлюза (админ) | root на сервере, код, БД, сеть, логи, возможность менять код | читать файлы/команды пользователей, действовать их устройством, входить в их аккаунт на панели |
| Внешний атакующий | публичный URL | перечислять пользователей, подбирать коды, захватывать аккаунты |
| Пользователь A | своя сессия, свой link-key | доступ к устройствам пользователя B |
| Облачный агент (Gemini/ChatGPT) | токен/ссылку пользователя A | доступ к B, эскалация прав |

Отдельно: **админ не должен уметь входить в панель как пользователь** — это значит, что сессия
панели не должна быть подделываемой на сервере. Сейчас в форке сессии живут в памяти процесса
(`gateway_identity.py`), значит админ с доступом к серверу может их создать/прочитать. Это тоже
устраняется только криптографией (клиентский ключ подписи сессии) или вынесением панели на
отдельный, не администрируемый оператором контур.

## 3. Пять уровней защиты (L0 → L4)

| Уровень | Идея | Что останавливает | Что **не** останавливает |
| :--- | :--- | :--- | :--- |
| **L0. Политика** | RBAC, 2-person rule, break-glass, логи | случайное/единоличное злоупотребление | целеустремлённого админа с root |
| **L1. Ключи у клиента** | сервер хранит только публичные ключи; link-key выводится на клиенте | выдачу/кражу bearer-секретов с сервера | чтение живого трафика (терминация) |
| **L2. Шифрование at-rest** | per-tenant URK/DEK, AEAD, имена/превью зашифрованы | дамп БД/диска/бэкапа | live-трафик |
| **L3. Blind relay (E2E)** | MCP-сервер на устройстве, HPKE/Noise клиент↔устройство, шлюз — релей | чтение/подмену содержимого оператором | метаданные, DoS, подмену кода доставки |
| **L4. Аттестация** | reproducible builds, подписи, TEE/confidential computing, transparency log | подмену кода шлюза и сокрытие доступа | украденный ключ пользователя |

**Вывод:** настоящий ответ на вопрос — **L3 + L4**; L0–L2 обязательны как гигиена, но не решают
задачу. Ниже — как это реализовать в этом проекте.

---

## 4. L1: ключи и идентичность — у пользователя, не на сервере

### 4.1. Устройство с ключевой парой

- Узел генерирует `Ed25519` (или `P-256`) при установке; приватный ключ — в OS keychain/DPAPI,
  публичный уходит на шлюз при привязке.
- При подключении узел подписывает `hello` (nonce шлюза + timestamp). Шлюз проверяет подпись.
  Device token остаётся как транспортный секрет, но **не является единственным доказательством**.
- Ротация: новая пара подписывается старой (цепочка), либо требует подтверждения на устройстве.

### 4.2. Link-key перестаёт быть серверным секретом

Сейчас `registry.json` хранит `link_key` в открытом виде. Варианты:

| Вариант | Как | Кто может восстановить ключ |
| :--- | :--- | :--- |
| A. Хранить только `sha256(link_key)` | ключ известен только установщику/пользователю | никто (включая админа) |
| B. Выводить ключ на клиенте: `HKDF(master_secret, user, device_pub)` | сервер получает производный идентификатор | пользователь (имея master_secret) |
| C. Одноразовые токены с TTL (15 мин) + refresh через подпись устройства | сервер не хранит долгоживущий секрет | никто |

Рекомендация: **A + C** для MCP-URL, **B** — для «одного адреса навсегда» (см. v2 §4.3).
Практически: `registry.user.link_key_sha256`, выдача полного ключа один раз при привязке;
повторная выдача — только по подписи устройства.

### 4.3. Панель: сессия, которую нельзя подделать на сервере

- Cookie остаётся, но в сессию добавляется **ключ подписи, производный от пароля/WebAuthn пользователя**
  (или passkey), так что сервер не может создать валидную сессию без участия клиента.
- Более простой шаг: `WebAuthn`-второй фактор для чувствительных действий (rotate/revoke) —
  сервер не сможет их выполнить без аутентификатора пользователя.
- Ещё проще и честнее: **не хранить ничего, что даёт админу аккаунт пользователя** — Google refresh
  tokens не хранить (в форке их и нет), email/sub — только для отображения.

### 4.4. Привязка без доверия к серверу

- Код пары показывается **на устройстве** и сверяется пользователем (SAS, 4–6 символов) —
  уже есть в референсе, но сейчас он не обязателен.
- Подтверждение пары подписывается ключом устройства, так что «одобрить» может только владелец
  устройства, а не админ через админ-токен (или админский путь остаётся, но помечается
  `pair_source=admin` и требует 2-person rule).

## 5. L2: шифрование at-rest (чтобы дамп сервера был бесполезен)

Из v2-плана (§5.3), минимум:

```
URK (32 B, только на устройствах пользователя)
 ├─ HKDF("rhm/tenant-kek") → KEK тенанта
 │    └─ AEAD(KEK, DEK, aad=object_id) → wrapped DEK
 │         └─ AES-256-GCM(DEK, данные) → файл/имя/превью
 ├─ HKDF("rhm/approval") → K_approval (превью подтверждений)
 └─ HKDF("rhm/audit")    → K_audit (подпись чекпоинтов)
```

- `registry.json`/`account.db`: имена устройств, email, workspace — в зашифрованном виде
  (`name_enc`), открытым остаётся только `tenant_id`/`device_id`.
- Админ с дампом БД видит UUID и размеры, а не содержимое.
- Что это **не** закрывает: live-трафик при терминации. Поэтому L2 — необходимый, но не
  достаточный уровень.

## 6. L3: blind relay — единственный способ закрыть live-трафик

### 6.1. Схема

```
Клиент (MCP-клиент/локальный шим) ──HPKE/Noise IK──► Устройство (MCP-сервер на узле)
        │                                                   ▲
        └────────── TLS до шлюза, кадры-конверты ───────────┘
                    шлюз видит: tenant_id, device_id, размер, время
```

- Узел поднимает `core/server.py` (локальный FastMCP) и публикует **публичный ключ**; шлюз — L4-релей.
- Клиент получает публичный ключ устройства из аккаунта (подписанный/запинненный) и устанавливает
  сессию; шлюз не имеет ключей.
- Подмена шлюза обнаруживается пиннингом ключа; в аудит пишется отпечаток.

### 6.2. Ограничение, которое надо признать

Облачные MCP-клиенты (Gemini Connectors, ChatGPT, Claude Web) **не умеют** произвольный E2E:
они ходят по HTTPS к URL, который им дали, и ожидают MCP на том конце. Значит:

| Клиент | Возможен ли blind | Как |
| :--- | :--- | :--- |
| Локальные (Claude Code/Desktop, Cursor, свои скрипты) | **да** | шим на машине пользователя, E2E до устройства |
| Облачные (Gemini/ChatGPT/Claude Web) | **нет** в чистом виде | либо шлюз пользователя (self-host), либо аттестованный релей (TEE), либо «доверенный, но прозрачный» режим с явным предупреждением |

Это ключевой продуктовый выбор: **нельзя одновременно обещать «облачный агент достаёт до устройства»
и «оператор шлюза ничего не видит»**, если оператор — не пользователь. В документации это должно
быть написано прямо.

### 6.3. Компромисс для облачных клиентов

1. **Self-host по умолчанию**: шлюз ставится на машину пользователя/в его облако; оператор = пользователь.
2. **Публичный шлюз — только как релей с аттестацией** (TEE) и явным статусом «прозрачный оператор»
   (публикует версию, digest, SBOM, лог доступа).
3. **Режим «доверенный оператор»** — для тех, кому удобство важнее; в UI и README это написано.

## 7. L4: аттестация и обнаружимость

- **Подпись релизов и payload**: `minisign`/`cosign` для `core/*.py`, проверка в установщике;
  отказ без подписи. Убирает «сервер отдал другой код».
- **Reproducible builds** + публикация digest; `rhm verify` сверяет работающий код с релизом.
- **Transparency log**: шлюз публикует подписанный Merkle-root действий; устройство хранит
  последний известный root и жалуется на расхождение.
- **TEE (по желанию, для публичного шлюза)**: SGX/TDX/SEV-SNP с remote attestation; ключи
  запечатаны, админ не читает память. Дорого, но это единственный способ дать облачным клиентам
  E2E-подобную гарантию.
- **Аудит с проверкой клиентом**: цепочка `prev_hash`, подпись `K_audit`; админ не может тихо
  переписать историю.

---

## 8. L0: организационные меры (обязательны, но недостаточны)

- Разделение ролей: `support` (видит метаданные), `admin` (управляет жизненным циклом), `security`
  (аудит) — без права чтения содержимого.
- **Запрет админской выдачи пользовательских ключей**: rotate/revoke только по инициативе
  пользователя или устройства; админский путь — break-glass с 2-human approval, аппаратным ключом
  и громким аудитом.
- Никаких «debug»-эндпоинтов и impersonation в проде.
- DPA/политика: «оператор видит трафик в режиме terminating» — прямым текстом.
- Пентест перед публичным запуском (включая попытку оператора прочитать данные).

## 9. Матрица: угроза → мера → остаточный риск

| Угроза | L1 | L2 | L3 | L4 | Остаточный риск |
| :--- | :--: | :--: | :--: | :--: | :--- |
| Админ читает файлы/команды | — | — | ✅ | — | метаданные (размер/время) |
| Админ действует устройством | частично (подпись устройства) | — | ✅ | — | DoS, отказ в обслуживании |
| Админ выдаёт link-key | ✅ (ключ не хранится) | — | ✅ | — | перехват при выдаче |
| Админ входит в панель как пользователь | частично (WebAuthn) | — | — | — | если ключ панели на сервере |
| Дамп БД/бэкапа | — | ✅ | ✅ | — | имена/UUID |
| Подмена кода шлюза | — | — | — | ✅ | компрометация ключа подписи |
| Подмена кода узла при установке | — | — | — | ✅ (подпись) | локальный MITM |
| Перечисление пользователей | — | ✅ (шифрование имён) | — | — | тайминги/размеры |
| Перебор ссылок/кодов | rate-limit | — | — | — | — |

## 10. Дорожная карта для этого проекта

| Фаза | Что | Оценка | Закрывает |
| :--- | :--- | ---: | :--- |
| **A. Гигиена (1–2 нед.)** | ключи устройств (Ed25519) + подпись `hello`; `link_key_sha256` вместо plaintext; rate-limit; подпись payload; честный README | 5–7 pd | L1 частично, L4 частично |
| **B. At-rest (2–3 нед.)** | URK/DEK, шифрование имён/превью/workspace; аудит-цепочка | 8–12 pd | L2 |
| **C. Blind relay (4–6 нед.)** | `core/server.py` на узле, HPKE/Noise, пиннинг ключей, шим для локальных клиентов | 20–30 pd | L3 для локальных клиентов |
| **D. Публичный шлюз (опция)** | TEE-релей + attestation + transparency log + DPA | 20+ pd | L3/L4 для облачных |

До фазы C честная формулировка: **«шлюз — доверенная сторона; для полной приватности используйте
свой шлюз»**. Это не маркетинг, а точное описание модели.

## 11. Что можно сделать уже сейчас, без переписывания

1. **Self-host как рекомендованный режим** (документация + установщик по умолчанию поднимает шлюз
   на машине пользователя, а не подключает к публичному).
2. **Убрать `link_key` из registry** (хранить хэш; выдавать один раз).
3. **Убрать админский путь подтверждения пары** для аккаунтов с OAuth (только владелец + подпись
   устройства; админский путь — `MESH_ALLOW_ADMIN_PAIR=1` для лабораторий).
4. **Подпись `core/*.py`** и проверка в установщике — дешёво и сразу убирает «сервер отдал другой код».
5. **WebAuthn** на rotate/revoke — без него админ с root всё равно всё может, но это снижает
   случайные и удалённые злоупотребления.
6. **Прозрачность**: публиковать версию/дайджест шлюза и лог входов; дать пользователю команду
   `rhm verify-gateway`.

---

## 12. Итог в одну фразу

Админ шлюза не сможет получить доступ к пользователю только тогда, когда **ключи и расшифровка
находятся вне сервера**: устройство подписывает себя, клиент шифрует трафик до устройства,
сервер — релей, а не терминатор. Всё, что делается правами, ролями и аудитом, снижает риск
злоупотребления, но не устраняет возможность. Поэтому кратчайший путь — **self-host + подписанный
код + blind-режим для локальных клиентов**, а для облачных — честное предупреждение и, в
перспективе, аттестованный релей.
