# Оценка риска: форк `nicelight/remote-devices-mcp` и доступ к устройствам

**Дата:** 2026-11-18
**Объект:** `https://github.com/nicelight/remote-devices-mcp` @ `2bbc9a0` (форк `LevRa7/remote-harness-mcp`, версия 0.4.8)
**Вопрос:** может ли автор форка получить несанкционированный доступ к устройствам пользователей,
которые воспользовались его форком?
**Дополнительно:** перечень конкретных уязвимостей форка — в [VULN_REPORT_fork.md](VULN_REPORT_fork.md).

---

## 1. Короткий ответ

**Да — но не через скрытый «бэкдор», а через архитектуру и цепочку поставки, которые форк унаследовал
и усилил.**

| Сценарий использования форка | Может ли автор получить доступ | Почему |
| :--- | :--- | :--- |
| Пользователь подключает устройство к **его шлюзу** (`mcp.natureonzoom.win`) | **Да, полный доступ** | шлюз терминирует MCP открытым текстом, хранит link-key, выдаёт команды узлу; это его сервер |
| Пользователь ставит узел **его установщиком** с его шлюза | **Да, полный доступ к машине**, даже если потом сменит шлюз | установщик скачивает `core/*.py` с его сервера без подписи → произвольный код |
| Пользователь поднимает **свой шлюз** из его репозитория | **Нет прямого доступа** (по коду не найдено скрытых каналов), но остаётся доверие к его ветке и обновлениям | нет E2E; однако шлюз у него свой |
| Пользователь на официальном npm/установщике LevRa7 | **Нет** | другие домен и пакет; но см. §8 — та же схема «payload с сервера», просто сервер ваш |

Ключевой вывод: **OAuth-вход в его панель не защищает пользователя от оператора шлюза.** Google-логин
закрывает панель от посторонних, но сам шлюз по-прежнему видит и может всё. Это не дефект форка —
это свойство текущей архитектуры (режим `terminating`, без E2E), которая в вашем же плане v2
обозначена как «blind relay» только на будущее.

## 2. Что видит и может оператор шлюза (факты из кода)

1. **Весь JSON-RPC трафик в открытом виде.** Узел открывает `wss://<gateway>/ws/tunnel`, шлюз
   разбирает кадры и передаёт `tools/call` в обе стороны (`gateway.py`, `mcp_unified_endpoint` +
   `call_remote_tool`). E2E-шифрования нет: `core/agent.py` расшифровывает на узле только TLS
   до шлюза.
2. **Он может инициировать любые вызовы.** Узел не проверяет «кто именно» отправил команду:
   авторизация — это device token при подключении, а дальше шлюз доверенный. Значит оператор может
   вызвать `bash_exec`, `run_job`, `write_file`, `edit_file`, `read_file`, `device_capture`,
   `device_control`, `device_messages`, `serve_dir` — все они есть в `core/mcp_tools.py`.
3. **Он хранит link-key в открытом виде.** `new_node_entry()` пишет `"link_key": new_link_key()`
   в `registry.json` (device token — только `token_sha256`). Link-key — это полный доступ к MCP
   устройства (URL `/sse?user=…&token=lk_…`), т.е. оператору не нужно ничего подбирать.
4. **Админ-токен на его сервере.** `MESH_ADMIN_TOKEN` даёт `rotate`, `revoke`, `approve` любого
   устройства (`/v1/devices/{user}/rotate`, `…/revoke`, `/v1/devices/pair/{code}/approve`).
5. **Он поставляет код.** `installer_asset()` (`gateway.py`) отдаёт `install.sh`, `install.ps1` и
   все `core/*.py` со своего диска. Установщик качает 23 модуля именно с `https://${GATEWAY}/${f}`
   и **не проверяет ни хэш, ни подпись** (`install.sh`, строки ~957–971: голый `curl -fSL`).
6. **Он — значение по умолчанию.** В форке `core/domain.py`:
   `DEFAULT_PUBLIC_BASE_URL = "https://mcp.natureonzoom.win"`. Установщик с `PAIR=true` по умолчанию
   (`install.sh`, `install.ps1`) уводит naive-установку на его шлюз.
7. **Полный доступ по умолчанию.** `core/onboarding.py` пишет `MESH_READ_ONLY='1'` только если шлюз
   вернул `access: read_only`; `approve_pair()` такого поля не возвращает → на устройстве
   `MESH_READ_ONLY=0`, т.е. `bash_exec` разрешён.
8. **Он видит метаданные.** `POST /v1/devices/pair` принимает hostname/os/arch; Google-вход даёт
   email и `sub`; `mesh_status` — версию, платформу, состояние. Это ещё не доступ, но это сбор
   идентифицирующих данных о пользователях.

## 4. Живая проверка его шлюза (2026-11-18)

| Проверка | Результат |
| :--- | :--- |
| `GET https://mcp.natureonzoom.win/health` | `200 {"status":"healthy"}`, `Server: uvicorn`, `Via: 1.1 Caddy` — шлюз работает |
| `GET /account` | `200`, 4165 байт — панель настроена (OAuth включён) |
| `GET /pair?code=AAAA-BBBB` | `404` (страница «код истёк») — маршрут `/pair` есть |
| `GET /install.sh` | `200`, 105 726 байт, `PUBLISHED_DOMAIN="mcp.natureonzoom.win"`, `PAIR=true` |
| `GET /core/agent.py` | `200`, совпадает с репозиторием (нормализованный SHA-256 `09710e7d…`) |
| `GET /core/onboarding.py` | `200`, **не совпадает** с GitHub HEAD: отдаётся версия до коммита `e17a0185` |
| `GET /install.sh` vs репозиторий | **не совпадает**: отдаётся версия до коммита `2bbc9a06` |

Вывод из проверки: **то, что отдаёт его сервер, уже не равно публичному GitHub.** Сейчас различие
выглядит как отставание деплоя на один-два коммита, но технически это демонстрация: любой
пользователь, ставящий узел «одной ссылкой», исполняет код, который не может сверить с
репозиторием. И оператор может изменить его в любой момент — подписи и контрольных сумм нет.

## 5. Три сценария и границы риска

### A. Устройство подключено к его шлюзу — риск максимальный

Пользователь проходит его онбординг (Google → «Подключить устройство»), узел открывает туннель на
`mcp.natureonzoom.win`. Дальше:

- оператор читает все вызовы и результаты (файлы, вывод команд, скриншоты);
- оператор может сам вызвать `bash_exec`/`write_file` — это штатная работа шлюза;
- оператор может сменить link-key и выдать его любому клиенту;
- отзыв в его панели защищает от третьих лиц, но не от него.

Это не «взлом», а злоупотребление доверием: пользователь доверил машину его серверу. Но
формулировка «вход через Google» создаёт ложное впечатление, что доступ ограничен.

### B. Свой шлюз, но его код и/или его установщик — риск средний

- Если ставили **его `/install.sh`** — на машине уже его код (23 модуля с его сервера, без подписи).
  Дальше он может заложить что угодно, вплоть до обратного шелла, и это не будет видно в GitHub.
- Если ставили **из его git-репозитория** со своим `MESH_PUBLIC_URL` — код = его ветка, но шлюз ваш;
  прямого живого доступа нет. Остаются: доверие к его будущим коммитам и к тому, что вы скачали
  именно тот код.
- Обновления: онбординг пишет `MESH_UPDATE_AUTO=0`, поэтому узел не тянет релизы сам. Но оператор
  вашего шлюза (вы) может обновлять как угодно; он — нет.

### C. Официальный npm / установщик LevRa7 — риска со стороны автора форка нет

`npm view remote-harness-mcp` → `0.5.1`, `author: LevRa7`; `gemini-computer-use` → `0.4.5`, `LevRa7`.
Под именами вашего проекта форк не публиковался, поэтому `npx remote-harness-mcp` не тянет его код.

## 6. Таблица риска

| Вектор | Кто эксплуатирует | Вероятность | Влияние |
| :--- | :--- | :--- | :--- |
| Прямые вызовы через шлюз (MCP-терминация) | оператор шлюза | **высокая** (это штатная возможность) | полный доступ к ФС/командам |
| link-key из `registry.json` | оператор шлюза | высокая | доступ как у MCP-клиента |
| Произвольный код в `/core/*.py` при установке | оператор шлюза | **высокая** (уже расходится с GitHub) | RCE на машине пользователя |
| Дефолтный домен + `PAIR=true` | оператор шлюза | высокая | naive-установки уходят к нему |
| Админ-токен: rotate/revoke/approve | оператор шлюза | высокая | смена ключей, отзыв, привязка |
| Сбор email/hostname/OS | оператор шлюза | высокая | идентификация пользователей |
| Скрытый бэкдор в коде | автор форка | низкая (не найден) | — |
| Атака на устройства чужих шлюзов | автор форка | **очень низкая** | нет механизма: узел слушает только свой шлюз |

## 7. Что делать пользователям (чеклист)

1. **Не устанавливать с чужого домена.** Ставить из официального npm/GitHub вашего проекта; если
   используете форк — только `git clone` с фиксацией коммита и собственный шлюз.
2. **Проверить, куда смотрит устройство:**
   ```bash
   grep -E 'MESH_PUBLIC_URL|MESH_GATEWAY' ~/.config/remote-harness-mcp/agent.env
   cat ~/.config/remote-harness-mcp/domain.env
   # Windows: %USERPROFILE%\.config\remote-harness-mcp\agent.env
   ```
   Там должен быть **ваш** домен, а не `mcp.natureonzoom.win`.
3. **Проверить фактические соединения:** `ss -tnp | grep ':443'`, `Get-NetTCPConnection` — узел
   должен держать WS только к вашему шлюзу.
4. **Сверить отдаваемый payload с репозиторием:** `curl -s https://<gw>/core/agent.py | sha256sum`
   против файла из git. Расхождение — красный флаг.
5. **Ставить узел в отдельную VM/пользователя**, без личных файлов и сохранённых паролей; для
   телефона — отдельный профиль.
6. **Включить минимальные права:** `MESH_READ_ONLY=1`, отключить `MESH_DEVICE_PIM`, не включать
   `remote_control`, ограничить egress (только домен шлюза и Google).
7. **Не вставлять link-key в чужие коннекторы/логи** и ротировать его после любого подозрения.
8. Помнить: **любой шлюз (в том числе свой) видит трафик**. Если это неприемлемо — нужен blind-режим
   с E2E (см. `docs/remote_harness_mcp_v2_plan.md`, §5), а не «доверенный шлюз с OAuth».

## 8. Что сделать вам как мейнтейнеру

Одна и та же схема «payload с сервера» есть и у вас (`install.sh` сначала тянет `core/*.py` с
`https://${GATEWAY}`, затем падает на `raw.githubusercontent.com`). Разница в том, что у вас шлюз не
отдаёт `core/`, поэтому фактически код берётся с GitHub, а у форка — с его сервера. Рекомендации:

1. **Подпись релизов и установщиков.** `minisign`/`cosign` для `core/*.py`, проверка в
   `install.sh`/`install.ps1` до импорта; без подписи — отказ (или явный `--insecure`).
2. **Контрольные суммы в релизе** + проверка `Get-FileHash`/`sha256sum` в установщике.
3. **Не отдавать `core/` с шлюза** (или отдавать только с подписью): сейчас это превращает любой
   шлюз в точку распространения кода.
4. **README: раздел «форки и доверие»** — явно: «используйте только официальный домен/пакет; шлюз
   оператора видит ваши вызовы; OAuth в панели не защищает от оператора».
5. **Реестр официальных доменов/отпечатков** и команда `rhm verify-gateway` (сверка отпечатка
   ключа/домена с релизом).
6. **Ускорить blind-режим** (E2E на устройстве): это единственный способ, при котором оператор
   шлюза не читает данные. До него — честная формулировка в документации.
7. **Мониторинг подмены:** искать в публичных установщиках свой `PUBLISHED_DOMAIN`/`package name`;
   при обнаружении — предупреждение пользователям (у форка `package.json` всё ещё
   `"name": "remote-harness-mcp", "author": "LevRa7"` — это путает, хотя в npm он не публиковался).

## 9. Как проверить самостоятельно (сводка команд)

```bash
# 1. Куда реально подключён узел
cat ~/.config/remote-harness-mcp/domain.env
grep -E 'MESH_(PUBLIC_URL|GATEWAY)' ~/.config/remote-harness-mcp/agent.env

# 2. Что отдаёт шлюз и совпадает ли с git
curl -fsS https://<gw>/core/agent.py | sha256sum
git show HEAD:core/agent.py | sha256sum

# 3. Какие маршруты вообще есть у шлюза (наличие публикации кода = доверие к серверу)
curl -fsS -o /dev/null -w '%{http_code}\n' https://<gw>/install.sh
curl -fsS -o /dev/null -w '%{http_code}\n' https://<gw>/core/mcp_tools.py

# 4. Кто автор пакета, которым ставили
npm view remote-harness-mcp version author repository.url
```

## 10. Ограничения этого анализа

- Проверены **4 коммита автора форка** и ключевые файлы; полный аудит 200+ файлов не проводился.
- Живая проверка — только `GET`-запросы к публичным страницам; внутрь шлюза доступа нет.
- Отсутствие найденного бэкдора **не доказывает** его отсутствие: сервер уже отдаёт версию,
  отличную от GitHub, и может отдать любую другую.
- Юридически форк легален (MIT), вопрос — в доверии и информированности пользователей, а не в
  нарушении лицензии.
