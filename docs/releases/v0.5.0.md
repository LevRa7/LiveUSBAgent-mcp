# Remote Harness MCP 0.5.0 — the node can be steered, and it remembers

24 tools became **28**: the node gained three ways to be driven from the chat
(`node_control`, `goal`, `schedule`) and one to look at its own screen
(`screen_capture`). Everything that used to require walking to the machine —
read-only, the working directory, the isolated container, pause — is now an MCP
call; and a long task no longer has to fit into a 30-second tool call.

## New tools

| Tool | What it does |
| :--- | :--- |
| `node_control` | The node's own switches: `status`, `mode` (`read_only`/`approval`/`full`), `cd` (the working directory every other tool resolves against), `pause`/`resume`, `sandbox` (the isolated Docker/Podman container) and `remote_control`. Changes apply to the next call; nothing restarts. |
| `goal` | The objective this chat is working on, stored on the node: `set`, `get`, `complete`, `blocked`, `clear`. It survives a reconnect, an agent restart and a new session — the next `initialize` carries it back into the session instructions. |
| `schedule` | Timers, the honest answer to "a tool call must return in ~30 s". `after_sec`, `every_sec` (≥10) or `at="HH:MM"` daily, with an optional command that starts as a background job when it fires. The firing becomes a *continuation*: it is injected into the session instructions and `mesh_status` until it is acknowledged with `schedule(action="ack")`. |
| `screen_capture` | The desktop of the node it runs on: GDI on Windows, CoreGraphics on macOS. A headless server answers `available: false` with the reason instead of a black image. **Linux has no portable screen API** — an X11 session needs a client library the node does not ship, Wayland refuses cross-client pixels, and a server has no display — so Linux reports that honestly rather than pretending. |

## Approvals: a confirmation continues the call

In `approval` mode a mutating call used to end with `approval_required`, which
made the model stop after every step and ask the user to continue. Now the node
**queues the call, waits for the operator and runs it in the same call**:

- `a` in `rhm` approves once and the waiting call continues;
- `A` (or `rhm approvals allow`) allows everything until revoked — one press for
  a whole task; `R` (`rhm approvals off`) restores the prompt;
- changing the access mode revokes a standing "always", so switching to approval
  means approval again;
- the cabinet (`/account`) no longer asks the node to approve the owner's own
  click — a logged-in person is not a model.

## The cabinet

`/account` now does something: a device is linked once by name plus its link key
(`lk_…`) or device token, and the page then shows and changes the same switches
as `rhm` — the remote-control lock first (right after login, with the warning
that it can only be turned back on at the machine), then mode, working directory,
isolation and pause. Cabinet buttons, the console menu and `rhm` subcommands all
go through one implementation, `core/settings.py`, so they cannot disagree.

## `rhm` without the menu

```bash
rhm status
rhm mode read_only|approval|full
rhm cd /path/to/project
rhm isolation on|off
rhm remote-control on|off
rhm pause | rhm resume
rhm approvals allow [minutes] | once | off
rhm goal "text" | rhm goal | rhm goal done "note"
rhm schedule | rhm schedule cancel <id> | rhm schedule ack [id]
rhm --json status
```

## One platform contract instead of scattered `if os.name` branches

Every OS-dependent behaviour lives in `core/platforms/` behind a single
`PlatformBackend` contract, and `core/mcp_tools.py`, `core/vitals.py` and
`core/device.py` delegate to it:

- **Windows** — telemetry, process tree and screenshots through Win32/ctypes
  (`GlobalMemoryStatusEx`, `GetSystemTimes`, `GetDiskFreeSpaceExW`, Toolhelp32,
  GDI). No PowerShell, WMI, `taskkill` or Git is required, and a clean install
  answers.
- **Linux** — `/proc` and `/sys` replace `df`/`free`/`ps`/`uptime`; process
  control is a syscall.
- **Android** — `/proc` + `/sys` first, Termux:API only where Android forbids the
  rest (camera, SMS, location, clipboard).
- **macOS** — `sysctlbyname` and `statfs` for telemetry (the numbers Activity
  Monitor shows), `libproc` for liveness and resident memory, CoreGraphics for a
  screenshot, `pbcopy`/`pbpaste` for the clipboard. The backend was announced in
  an earlier commit but not actually built; it exists now, and a test builds it
  on every host.

## Fixes

- **Background jobs stream.** A Python child whose stdout is a pipe
  block-buffers, so a long download reported nothing for minutes and looked
  stuck; every child now gets `PYTHONUNBUFFERED=1` unless the operator set it.
- **One configuration directory.** The agent wrote its heartbeat to the new
  directory while `rhm` and the watchdog read the pre-rename one, so a connected
  node looked dead and the watchdog could start a duplicate. The agent now
  resolves the directory through `control.control_dir()`.
- **The watchdog, the doctor and the updater find the node again.** They chose
  the configuration directory by "does the new path exist", and a cabinet
  database was enough to create it; `agent.env` decides now.
- **The gateway reports its public host.** `core/domain.py` was importable but
  its own import failed on the deployed layout, so `host` was empty.
- **The bootstrap lists carry every module.** `core/goal.py`,
  `core/schedule.py`, `core/settings.py` and `core/web_settings.py` are fetched
  by `install.sh`/`install.ps1`, so a fresh node is not missing a module a tool
  imports.

## Upgrading

Nodes update themselves: the release publishes `mesh-payload-0.5.0.zip` with its
SHA-256, and `mesh_update` installs it, verifies the hash and restarts. The token
and the MCP URL already in Gemini are unchanged — see 0.4.8 if that question is
new. `npx remote-harness-mcp@0.5.0` and the `gemini-computer-use` alias publish
the same code.
