# Remote Harness MCP 0.5.2 — links follow the bridge, shares render correctly

A patch release for 0.5.1. It fixes four defects that made published files and
pages come back broken, and one that made every link name a domain the gateway
was no longer reached at.

## What was broken

1. **Published links named the wrong domain.** `core/web_share` builds
   `<domain>/<node>/<slug>/…` from `core.domain`, whose last fallback is the
   built-in default. On Windows the configured `domain.env` had been written to
   the pre-rename directory, and once the new config directory existed the
   resolver stopped looking there: the node silently fell back to the built-in
   default and minted every share and page link on `smart-server.online` while
   its tunnel went to the Tailscale name. Tokens (printed by the gateway) and
   links (printed by the node) disagreed, and only machines with a `hosts`
   override could open the links at all.

2. **Text shares rendered as mojibake.** The share server answered
   `Content-Type: text/plain` with no charset, so a Russian Windows decoded the
   UTF-8 bytes as windows-1251: `как` became `РєР°Рє`.

3. **A published site returned 404 for its own assets.** The nginx snippet
   answered 404 for `.json`, `.log`, `.conf`, `.env`, `.yml`/`.yaml`, `.bak`,
   `.old`, `.sql`, `.ini` paths and for `/vendor/`, `/node_modules/`,
   `/wp-content/`, `/wp-admin/` — scanner-noise control that also matched real
   files inside a share (`manifest.json`, `package.json`, a vendored bundle).

4. **A BOM in `shares.json` emptied the share registry.** PowerShell writes one
   with `Set-Content -Encoding UTF8`; `json.load` then failed, the failure was
   swallowed as "no shares", and every published link answered 404.

5. **The served `install.sh` had CRLF line endings** (published from a Windows
   checkout), so `curl … | bash` died on `$'in\r'`.

## The fix

- The gateway announces its public domain to every node when the tunnel
  connects (`{"type":"hello","public_base":…}`) and the node adopts it for all
  link generation (`core.agent.apply_gateway_hello`). **One config — the
  gateway's `domain.env` — switches tokens, file links and page links
  together**; a node's own `domain.env` remains the fallback for a gateway that
  does not announce one. Nodes log `Public links: <url> (source: …)` at startup,
  so a silent fallback can no longer hide.
- Text responses carry `; charset=utf-8`, added by the node's share handler and
  by the gateway's relay (which also covers a node still running older code).
  An explicit charset sent by the node is never overridden.
- The share namespace `/<node>/<slug>-<16 hex>/…` is matched **before** the
  scanner rules in the nginx snippet.
- `shares.json` is read with `utf-8-sig`.
- The published installers bake the domain and are served with LF.

New tests pin the relay charset (including the "node sends no charset" case and
that an explicit charset survives), the BOM-tolerant registry, the hello payload
and its adoption by the node.

## Upgrading

Nodes update through `mesh_update` / `npx` as usual. A node that keeps its own
`domain.env` keeps working either way; once it runs 0.5.2 it also follows a
domain change made on the gateway alone.
